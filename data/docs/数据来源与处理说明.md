# 数据来源与处理说明

> 广州北环高速公路平纵联合线形优化 —— 全部外部数据的来源、可信度、处理链与使用方式
>
> 本文档目标：任何人拿到本分支，都能回答三个问题——**数据从哪来**、**凭什么可信**、
> **在模型里到底被用在哪一步**；并且能按文中命令**从零复现**每一个派生文件。

---

## 0. 数据总览

本项目的数据分三类，来源性质完全不同，可信度也必须分开评估：

| 类别 | 文件 | 性质 | 是否进入目标函数 |
|---|---|---|---|
| **实测数据** | `measured/数据.xlsx` | 项目实测（GPS 中线 14018 点） | 是（基准线位、地面高程、曲率） |
| **DEM 高程** | `dem/走廊带DEM_z14*.npz` | 第三方公开栅格（AWS Terrain Tiles） | 是（新线位的地面线、生态区判定） |
| **OSM 矢量** | `osm/obstacles/obstacles.npz` | 第三方众源矢量（OpenStreetMap） | 是（立交带空间锚定 → 土方豁免与桥隧计费） |
| | `osm/buildings/buildings_full.npz` | 同上 | **否**（仅可视化与走廊带宽度论证） |

一条贯穿全文的原则：**实测数据优先**。第三方数据只在实测数据无法覆盖的地方使用
（实测只有一条中线，而优化会生成偏离中线的新线位，新线位下的地面高程只能靠 DEM），
并且每一处使用都必须给出与实测数据的一致性核验。

## 1. DEM 高程数据

### 1.1 为什么需要它

纵断面优化要算土方量，土方量 = f(设计高程 − **地面高程**)。实测数据只给出了
**既有中线上**的地面高程；而平纵联合优化会把线位在走廊带内左右挪动，挪动后的
新线位踩在哪里、那里地面多高，实测数据答不了。因此必须有一个**面状**的高程模型。

### 1.2 来源

| 项 | 内容 |
|---|---|
| 数据集 | AWS Terrain Tiles（terrarium 编码） |
| 注册页 | https://registry.opendata.aws/terrain-tiles/ |
| 瓦片 URL | `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png` |
| 项目文档 | https://github.com/tilezen/joerd （Joerd，原 Mapzen，现社区维护） |
| 编码规范 | https://github.com/tilezen/joerd/blob/master/docs/formats.md |
| 访问方式 | 公开、免密钥、免注册 |
| 许可 | 各来源数据集自身许可（SRTM/NED 等为公有领域或宽松许可），详见 Joerd 文档 |
| 本项目用的缩放级 | `z = 14` |

**它本身不是原始测量数据，而是一个"拼装产品"**：Joerd 把多个国家级/全球级高程数据源
按优先级镶嵌成全球无缝瓦片。在中国境内、z14 这一级，其底数主要来自
**NASA SRTM（航天飞机雷达地形测绘任务）1 弧秒版**（约 30 m 网格），
另有 GMTED2010、ETOPO1 等作为低分辨率兜底。

### 1.3 使用广泛程度

- AWS 把它收录进 **Open Data Sponsorship Program**（AWS 出钱托管的公共数据集计划），
  该计划的收录本身就是一道使用量与公共价值的筛选。
- 它是 Mapzen / Nextzen 地形服务的底层数据，Tangram、OpenMapTiles 等开源地图渲染
  管线的地形晕渲（hillshade）与等高线普遍以它为源。
- SRTM 作为其主要底数，是**地球科学界使用最广的免费全球高程数据**，被数万篇论文引用，
  是水文、地貌、遥感、工程选线等领域的事实标准基线数据。

### 1.4 可信程度（含必须承认的局限）

**外部指标（SRTM 任务规格）**：绝对垂直精度约 ±16 m（LE90，即 90% 置信），
相对垂直精度优于绝对精度；实际在平缓地区常见 RMSE 约 6~10 m。
这是"区域地形形态可信、单点绝对高程有系统性偏差"的典型量级。

**本项目自己的核验（这是最有说服力的一条）**：
沿实测中线逐点采样 DEM，与 GPS 实测高程对比：

| 指标 | 数值 | 含义 |
|---|---|---|
| 相关系数 | **0.915** | 地形起伏形态与实测高度一致 |
| 中位偏差 | **+1.57 m** | 系统性垂直基准差，可用常数消除 |

处理上以常数 `BIAS_M = 1.57` 消除该基准差（DEM 为正高、GPS 为高程，二者基准不同，
存在常数偏移属正常现象），消除后残差已进入工程可接受范围。

**必须诚实说明的两条局限**：

1. **分辨率被"过采样"**。z14 在本纬度（23.16°N）的像元地面尺寸约 **8.78 m**，
   但底数 SRTM 是约 **30 m** 网格。也就是说 8.78 m 只是**瓦片像元尺寸**，
   **不是真实空间分辨率**（约过采样 3.4 倍）。因此 DEM 能可靠反映数百米尺度的
   地形起伏（山体、垭口、河谷），**不能**用于判读单栋建筑级或路基边坡级的微地形。
   本项目的用法（土方量按平均断面法沿 10 m 桩号积分、生态区按连片山体判定）
   都在这个可靠尺度之内。
2. **它是"现状地表"，不是"建路前的天然地面"**。既有北环高速的路基已经"长"在
   DEM 里了 —— 这会造成严重的口径不公，处理办法见 §1.6。

### 1.5 处理链（一）：下载与拼接

脚本：`dem/fetch_dem_ext.py`

1. 覆盖范围取 `lon 113.159~113.423, lat 23.095~23.201`
   （实测线位外扩约 2.8 km，足以支撑 ±2.5 km 走廊带的搜索）；
2. 换算为 z14 瓦片索引，下载 **60 张**瓦片并拼接为 **1280 × 3072** 栅格；
3. 按 terrarium 规范解码高程：

   ```
   h = R × 256 + G + B / 256 − 32768        （单位 m）
   ```

4. **坏点清理**：terrarium 源存在个别 `< −100 m` 的异常值（实测到 −936 m），
   按 3×3 邻域中值填补；下游读取时再次以 `< −100 m` 过滤兜底。

产出：`dem/走廊带DEM_z14_ext.npz`，字段 `elev / z / x0 / y0 / H / W`。
（`dem/走廊带DEM_z14.npz` 是更早的窄范围版本，保留仅为历史可追溯。）

#### 一处实际覆盖范围的偏差（由复核脚本查出，如实记录）

栅格为 **1280 行 = 整 5 张 z14 瓦片 = 11238 m**，而标称 bbox 的纬度跨度
`23.095~23.201`（0.106°）需要约 **11800 m**，即需要 **6 张**瓦片。
因此 DEM 的**实际南界是 lat 23.09998**，比标称 bbox 的 23.095
**短约 555 m**（瓦片索引按整张取，南边少取了一行瓦片）。

**对模型无影响**，理由是可验证的：实测线位的 Y 范围是 **−524 ~ 2100 m**，
即便取本项目搜索过的最宽走廊带 **±2500 m**，也**完全落在 DEM 覆盖内**
（复核脚本对 ±500 m 与 ±2500 m 两档均做了断言）。这个缺口位于**线位以南约 6 km**，
高程采样永远不会触及。

**唯一后果是绘图上的**：最南端的一小部分建筑落在 DEM 底图之外，
叠加图上那里没有地形底色。属观感问题，不影响任何计算。

### 1.6 处理链（二）：准天然地面重建 —— 本项目最关键的一处数据订正

**问题**：DEM 是现状地表，既有路基已包含在内。于是沿现状线位
`|设计高程 − 地面高程| ≈ 0`，**现状方案的历史土方成本被算成了零**；
而优化出的新线位踩在未整形的天然地面上，要付全额土方费。
两者口径不一致 —— 这会系统性地偏袒现状方案，让任何优化都"看起来更贵"。

**处理**（`dem/dem.py::build_natural()`）：
把实测中线两侧 `±MASK_HALF_W = 60 m`（路基半宽 25.5/2 + 边坡 + 施工带）的像元
**掩膜移除**，再用影响带**外**的邻域像元线性插值回填，得到
"移除道路后的准天然地面"。这是遥感/GIS 领域标准的
**DEM restoration / road removal** 做法。

此后**所有方案（含现状）统一对准天然地面计算土方**，口径公平性得以恢复。

产出：`dem/走廊带DEM_z14_ext_natural.npz`，字段
`natural / eco / mask_half_w / eco_elev / eco_close`。

> **局限声明**：建路前的实测地形不可得，"准天然地面"是插值近似而非真实历史地面。
> 论文中据实声明该近似即可；它的作用是**消除口径偏差**，不是还原历史真值。

### 1.7 处理链（三）：白云山生态强制隧道区

依论文 §2.1.1 选线原则（优先避让自然保护区，确需跨越时实施最小干扰），
穿越白云山风景区的线位**强制以隧道通过**，不允许大开挖。风景区边界不采用人工划线，
而以可复现的客观规则界定（`dem/dem.py::eco_mask_xy`）：

> 准天然地面高程 **≥ 70 m** 的连片山体，再做尺度约 **500 m** 的形态学闭运算
> （把山体内部的沟谷、垭口并入连片区，与"隧道连续穿越山体"的工程事实一致）。

**双指标校准**（这是该规则可信的依据）：

| 校准指标 | 本规则给出 | 实际值 | 偏差 |
|---|---|---|---|
| 风景区面积 | 19.2 km² | 约 21 km² | −8.6% |
| 现状线穿越长度 | 1.28 km | 1.35 km（实际白云山隧道） | −5.2% |

两个独立指标同时落在 10% 以内，说明 70 m / 500 m 这组参数不是拟合出来的巧合。

### 1.8 模型里到底怎么用

`dem/dem.py` 对外暴露的接口，以及它们在优化中的位置：

| 接口 | 作用 | 被谁调用 |
|---|---|---|
| `ground_elev_xy(X, Y, lat0, lon0, natural=True)` | 双线性插值取地面高程（连续可微，保证目标函数对平面偏移连续） | `objective_joint.decode_joint` → `gz_new`（新线位地面线） |
| `eco_mask_xy(X, Y, lat0, lon0)` | 逐桩号判定是否落在生态强制隧道区 | `decode_joint` → `eco` 掩膜 → `exempt` 与 `L_eco_km` |
| `xy_to_lonlat / lonlat_to_px` | 模型局部坐标 ↔ 经纬度 ↔ 栅格像元 | 上述二者内部 |
| `build_natural()` | 生成并缓存准天然地面 | 首次运行自动触发 |

**关键点**：`ground_elev_xy` 用**双线性插值**而非最近邻，是为了让地面高程对平面偏移
**连续可微** —— 否则 IJS 在搜索平面时会遇到阶梯状目标函数，优化会卡在台阶上。

### 2.1 来源

| 项 | 内容 |
|---|---|
| 数据库 | OpenStreetMap |
| 主站 | https://www.openstreetmap.org |
| 版权与许可页 | https://www.openstreetmap.org/copyright |
| 许可 | **ODbL v1.0**（Open Database License），https://opendatacommons.org/licenses/odbl/1-0/ |
| 查询接口 | Overpass API，https://overpass-api.de/api/interpreter |
| 接口状态页 | https://overpass-api.de/api/status |
| 接口文档 | https://wiki.openstreetmap.org/wiki/Overpass_API |
| 查询语言参考 | https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL |

**署名要求（ODbL 强制）**：任何公开使用须署名
**"© OpenStreetMap contributors"**；基于本数据的衍生数据库须以 ODbL 同等条款共享。
本分支所有 OSM 派生文件的脚本头部均已写入该署名。

### 2.2 使用广泛程度

OSM 是**世界上最大的开放地理数据库**，注册贡献者约 1000 万量级。
其被工业界与学术界大规模采用的事实包括：

- **商业地图产品**：Apple Maps、Meta（Facebook）、Amazon、Microsoft（Bing Maps）、
  Tesla 等公司的地图产品均在不同程度上使用 OSM 数据；
- **人道主义响应**：Humanitarian OpenStreetMap Team（HOT）、Missing Maps 在灾害响应中
  以 OSM 为基础底图，被联合国机构与红十字会采用；
- **学术研究**：OSM 是交通网络分析、可达性研究、城市形态学的常用数据源，
  相关文献数以万计。

### 2.3 可信程度（分要素、分地区，不能一概而论）

OSM 是**众源（crowd-sourced）**数据，其完备度与要素类型、地区高度相关，
必须分开评估，不能用一句"OSM 很准"或"OSM 不准"概括。

**道路网**：学界较一致的结论是，OSM 道路网在多数国家已接近完备
（Barrington-Leigh & Millard-Ball, *PLoS ONE* 2017 的全球评估是该结论的常被引用来源），
主干路网（motorway/trunk/primary）的完备度尤其高 —— 因为主干路显著、易被制图、
且被多个商业用户反复校核。**本项目只使用 motorway/trunk/primary/secondary 四级主干路**，
正落在 OSM 最可靠的部分。

**铁路、河渠**：同属显著地物，完备度高。

**建筑轮廓**：完备度**差异极大**，是 OSM 最不均衡的图层之一。发达城市中心区可能接近
完备，郊区与村镇缺失明显。中国境内建筑测绘完备度整体低于欧美。
**这正是本项目把建筑数据严格限定为"仅可视化、不进入目标函数"的原因**（见 §2.6）。

**本项目自己的核验**：见 §2.5 的立交带命中验证与 §2.6 的数量核对 —— 我们不依赖
对 OSM 的笼统信任，而是对每一处具体用法都做了独立验证。

### 2.4 处理链（一）：走廊带障碍物（道路/铁路/水系）

**用途**：优化线位横穿既有城市道路、铁路、河渠时必须跨越（上跨或下穿），
这决定了立交/桥梁的空间位置与计费。

**查询语句**（`osm/obstacles/query.overpass`，原文照录）：

```
[out:json][timeout:60][bbox:23.095,113.159,23.201,113.423];
(
  way[highway~"^(motorway|trunk|primary|secondary)$"];
  way[railway=rail];
  way[waterway~"^(river|canal)$"];
);
out geom;
```

**抓取记录（可追溯）**：

| 项 | 内容 |
|---|---|
| 端点 | `https://overpass-api.de/api/interpreter` |
| 查询时间 | 2026-08-09 15:04:28 UTC |
| 数据快照 `timestamp_osm_base` | 2026-08-09T15:03:11Z |
| Overpass 版本 | 0.7.62.11 |
| bbox | `23.095, 113.159, 23.201, 113.423`（与 DEM 完全一致） |
| 原始返回 | `raw_overpass.json`（5.43 MB，6132 个 way，全部带 geometry） |

> 抓取过程如实记录：主端点首次遇服务器繁忙、二次因传输超时中断，
> 镜像 `overpass.kumi.systems` 亦繁忙，最终主端点加 gzip 压缩成功。

**处理**（`osm/obstacles/process.py`）：分类为 `road / rail / water` 三类，
经纬度转模型局部平面坐标，产出 `obstacles.npz`（**6002 条折线**：
road 4807 / rail 857 / water 338），字段
`lines_lon / lines_lat / offsets / kind / highway_class / name / osm_id`。

### 2.5 障碍物数据的验证：立交带命中检查

论文给出既有 7 座功能性立交的桩号带。我们用 OSM 障碍物独立检查
"这 7 个桩号带内是否真的存在横贯走廊带的被交道路" —— **7 个带全部命中**，
命中要素如广园西路、机场路、机场高速、许广高速、石井河等，
最少 6 个、最多 54 个 way。结论：无需补充 tertiary 级道路，数据足够支撑立交锚定。

> **一处必须记录的坐标方向问题**：`数据.xlsx` 中线首点位于走廊带**东端**
> （lon 113.38835, lat 23.15442），即**累计里程 0 在东侧（黄村端）**。
> 由命中要素可见，桩号带 20300–20900 命中"金沙洲路"（西端浔峰洲侧），
> 200–1000 命中"广州东环城际线"（东端），说明论文表中给定的立交**名称**
> 与实际地理位置呈**东→西反序对应**。无论名称如何对应，7 个桩号带内均存在
> 横向障碍物要素，锚定逻辑成立。此项不影响计算，但读图时必须知道。

### 2.6 处理链（二）：建筑轮廓（完整集）

**用途（严格限定）**：可视化图层 + 走廊带宽度的数据依据论证。
**不进入目标函数，不参与任何成本/能耗计算。**
这一限定是有意的 —— 见 §2.3 中建筑图层完备度不均衡的说明。

#### 旧版本的三处缺陷（已废弃，保留可追溯）

`osm/buildings/buildings.npz` 由 `fetch_buildings.py` 生成，**不应再使用**：

1. 用 `out center` 只存**质心**，没有建筑轮廓；
2. 只查 `way["building"]`，**漏掉 177 个多重多边形关系**（`relation["building"]`）；
3. bbox 被裁窄为 `23.1264~23.1966 / 113.1669~113.4137`，比 DEM/障碍物范围小一圈。

结果旧文件只有 **12789** 个点，**仅为实际 22414 个 way 的 57%**。

#### 完整集的抓取与核验

**先定"标尺"再抓数**：先用 Overpass `out count` 取权威计数作为硬指标，
再分块抓取并逐项对齐 —— 否则"抓了多少算全"永远说不清。

抓取（`osm/buildings/fetch_buildings_full.py`）：bbox 切 **16 × 8 = 128 块**，
三类要素共 **384 次** `out geom` 查询，带指数退避重试、端点轮换、分块落盘可断点续抓。
**零失败**。

处理（`osm/buildings/process_buildings.py`）：按 `(type, id)` 去重
（跨块边界的建筑会在相邻块重复返回）→ 多重多边形按 role 分内外环并**缝合成闭合环**
（OSM 多重多边形外环常被拆成多段 way）→ 计算质心与面积 → **与目标量逐项核对**。

**核验结果：三项全部完全一致**

| 要素 | 实得 | `out count` 目标 | 结论 |
|---|---|---|---|
| `way["building"]` | 22414 | 22414 | 一致 |
| `relation["building"]` | 177 | 177 | 一致 |
| `way["building:part"]` | 397 | 397 | 一致 |

合计 22414 + 177 = 22591 个建筑要素，其中 **1 个几何退化**
（一个 relation 的成员无法缝成闭合环）被剔除，最终
**22590 个建筑、22787 个环、171039 个顶点、总占地 24.41 km²**
（中位 519 m²，最大 145133 m²）。类型分布：`yes` 11407、`residential` 3526、
`apartments` 3163、`commercial` 865、`university` 660、`house` 547 等。

#### 快照一致性修正（一个容易被忽略的坑）

首轮抓取中镜像 `overpass.kumi.systems` 返回的是**它自己的旧快照**，
27 个分块的 `timestamp_osm_base` 最早到 **2026-05-06**，比目标快照旧近 3 个月。
混用不同时刻的快照会使总数对不上（当时 way 少 10 个），
且**数据自身不自洽**（相邻块可能反映不同时点的地物）。

处理：`osm/buildings/refetch_stale.py` 仅经主端点重抓这 27 块，并断言返回快照日期，
使**全部 384 块的 `osm_base` 落在同一天**；重新核对后三项计数全部一致。
数据集内保存 `osm_base` 字段可供复核。

> 教训：镜像站点的数据新鲜度不保证与主站一致。凡分块抓取，
> **必须记录并校验每块的快照时刻**。

#### 为什么必须用轮廓而不是质心

横向净距应量到建筑**边缘**而非质心。最大建筑占地 14.5 万 m²，
其边缘比质心近上百米 —— 用质心会**系统性高估**可用宽度。
按轮廓顶点重算的走廊带可行半宽（两侧均无建筑冲突的里程占比）：

| 半宽 | ±100 m | ±200 m | ±300 m | ±500 m | ±800 m |
|---|---|---|---|---|---|
| 无冲突里程占比 | 71.6% | 58.0% | 49.3% | 34.6% | 18.2% |

左侧净距中位 550 m、右侧 719 m，**最紧断面仅 10 m**。
这组数据支持"走廊带不应全线取同一半宽"的结论。

#### 仍需注意的局限

数量已与 Overpass 计数完全一致，即**本 bbox 内 OSM 数据库中的建筑已全部取到**。
但 OSM 本身在国内城区的建筑测绘完备度并非 100%，因此**"图上空白"只能说明
OSM 中无记录，不等于实地无建筑**。此为数据源固有局限，非本次抓取的缺漏。
正因如此，建筑数据不进入目标函数。

### 2.7 模型里到底怎么用

| 数据 | 使用位置 | 作用 |
|---|---|---|
| `obstacles.npz` | `objective_joint._ic_bands_from_osm(X, Y, s, t_meas)` | 以 OSM 被交道路与实测中线的**交叉点**空间锚定 7 座立交的弦区间 |
| ↑ 产出的 `ic_bands` | `decode_joint` → `ic` 掩膜 | 落入立交带的桩号**土方豁免**（结构费已计入 CB 常数），并输出 `L_ic_km` |
| `ic_anchor_cache.json` | 同上 | 锚定结果缓存，避免每次重算 |
| `buildings_full.npz` | 绘图脚本（图C9 全图层叠加、fig4_full、fig6b/7b）；**以及 §2.8 密度聚类链的输入** | 可视化 + 走廊带宽度论证 + 密度分区 |
| `density_tiers_V1.npz` 的 `depth2` | `decode_joint` → `objectives_joint` 的 `pen` | **Tier2 禁行硬约束**（见 §2.8） |
| `density_tiers_V1.npz` 的 `tier1` | `decode_joint` → `info["soft_dense1"]` | **Tier1 可穿越软抑制**（不进 `pen`，见 §2.8） |

**关键点**：立交带是**空间锚定**而非固定桩号 —— 因为优化改变线位后里程轴会变，
写死桩号会让立交"漂移"到错误的地理位置。锚定到 OSM 实际交叉点才是正确做法。

### 2.8 处理链（三）：建筑密度聚类 → 线位分区约束

#### 为什么需要它

建筑轮廓本身只是一堆多边形，无法直接约束线位。工程上真正的问题是：
**哪些地方密到不该穿，哪些地方虽然有居民但可以穿**。既有北环高速本身就穿过了
一些居民区，所以这不是简单的"有建筑就禁行"，必须有分级。

#### 三级分区

| 分级 | 判据 | 在优化中的性质 |
|---|---|---|
| **Tier2 严格禁行** | `D > θ_forbid` 的连通密集核心 | **硬约束**：计入 `pen`，任何穿越即被可行性门控剔除 |
| **Tier1 可穿越但抑制** | `θ_pass < D ≤ θ_forbid` | **软代价**：**不进 `pen`**，作独立软项加到标量目标 |
| Tier0 自由 | `D ≤ θ_pass` | 无代价 |

> **为什么 Tier1 绝不能计入 `pen`**：`run_joint.py` 的可行性门控是
> `feas = [c for c in cands if c["pen"] <= 1e-6 and ...]`，**任何**非零惩罚都会让候选被剔除。
> 若把 Tier1 也算进 `pen`，Tier1 就退化成和 Tier2 一样的硬约束 —— 而现状线位 M-A 自己就有
> 2.00 km 落在 Tier1，"允许在一定范围内穿越"的设计目标会被**静默摧毁**。
> 故两级代价必须走两条通道。这是本节最容易踩错的一处。

#### 阈值不是手填的，而是由现状线位标定

手填阈值无法回答"凭什么这个密度不能穿"。既有高速已经建成并穿过居民区，
**这就是"该密度可以穿过"的经验铁证**。于是：

```
D_A(s)   = 现状线位沿程密度剖面
D_A_max  = max D_A(s)
θ_forbid = D_A_max × margin        (margin ≥ 1)
θ_pass   = θ_forbid × 0.5
```

`margin ≥ 1` 使 **M-A 基准方案在 Tier2 上天然可行，不需要任何特例豁免**。
这与 §1.7 生态区"面积 19.2 vs 实际约 21 km²、现状穿越 1.28 vs 实际 1.35 km"
的双指标标定是同一思路：**让既有事实去标定参数，而不是反过来**。

#### 聚类方法与选型

聚类沿用 §1.7 生态区界定的**同一套范式**（而不是另起一套）：

```
多边形栅格化 → 高斯平滑得邻域密度 → 阈值化 → 形态学闭运算 → 连通域标记 → 最小簇面积过滤
```

**为什么不用 DBSCAN / HDBSCAN**：① 仓库无 `sklearn` 依赖（`requirements.txt` 只有
numpy/scipy/pandas/matplotlib/openpyxl/python-docx），而 `scipy.ndimage` 已被 `dem.py` 使用；
② 更本质的原因是 DBSCAN 的 `eps / minPts` **无法对接"现状线位可穿"这个标定锚点**，
而覆盖率阈值有直接物理含义（建筑占地比），可以被现状线位直接标定。

共产出 6 个候选版本（指标 × 平滑尺度 × margin × 形态学后处理），
诊断表见 `../osm/buildings/README.md`。**选定 V1（方案A）**：

| 参数 | 取值 |
|---|---|
| 密度指标 | 建筑占地覆盖率（m²/m²，0~1） |
| 平滑尺度 σ | 200 m |
| margin | 1.15 |
| 形态学闭运算 | 100 m |
| 最小簇面积 | 1 ha |
| **D_A_max** | **0.1836** |
| **θ_forbid** | **0.2111** |
| **θ_pass** | **0.1056** |

V1 的诊断量：

| 诊断 | 值 | 含义 |
|---|---|---|
| Tier2 面积 / 簇数 | 27.29 km² / 35 簇 | 街区尺度的密集核心 |
| Tier1 面积 | 62.25 km² | 可穿越的居民带 |
| **M-A ∩ Tier2** | **0.000 km** | 基准方案天然可行（标定保证） |
| **M-A ∩ Tier1** | **2.000 km（8.9% 里程）** | "既有高速确实穿过居民区"的量化 |
| ±500 m 走廊带封堵断面 | 0 / 450 | 走廊带保持贯通 |
| ±500 m 最窄可通宽度 | 625 m | 优化仍有横向余地 |

#### 栅格化的一处修正与硬自检

先导测算曾把每栋建筑的**全部占地面积记到其质心所在网格**，使大于网格的建筑
覆盖率 > 1（非零格 90 分位达 1.248）—— 而覆盖率的物理上限是 1，这会直接污染标定。

正式实现改为：**5 m 子网格逐环点在多边形判定**（外环填充、内环即天井扣除），
再聚合到 25 m 网格。两道自检：

1. **总面积**：栅格总面积 23.792 km² vs 轮廓真实总面积 24.408 km²，偏差 **−2.52%**。
   这个偏差**是应有的**：22915 个 5 m 子格曾被相互重叠的轮廓累加到覆盖率 > 1，
   已截断至 1，截断量 ≈ 0.57 km²，与 0.616 km² 的差值吻合。地面覆盖率不应重复计数。
2. **覆盖率值域**：处理后严格落在 `[0, 1]`，超界格数为 0。

#### 一个会导致程序崩溃的阈值下界（务必留意）

先导测算发现：阈值取 **0.10** 时，±500 m 走廊带有 **2 个断面被完全封堵** ——
即走廊带内**不存在任何可行线位**。此时 `run_joint.py` 的
`feas = [... if c["pen"] <= 1e-6 ...]` 会得到空集，紧接着的 `front[...]` 直接抛异常。

**因此任何阈值方案在采用前都必须先做走廊带通行性检查**
（`building_density.corridor_passability`，报告完全封堵断面数与最窄可通宽度）。
本项目 6 个候选版本均已通过（最窄可通 525~1000 m）。

#### 产物与字段

| 文件 | 内容 |
|---|---|
| `density_grids.npz` | 25 m 基础栅格：`area`（占地 m²）/`count`（栋数）/`vol`（占地×层数） |
| `density_tiers_V1.npz` | 选定版本产物：`S` 密度场、`tier1`/`tier2` 掩膜、`depth2` 禁区内深度场（m）、`theta_pass`/`theta_forbid`/`D_A_max`、网格元数据 |

**`depth2` 为什么必要**：惩罚项若直接用布尔掩膜，在禁区**内部**是平台状的、
梯度恒为 0，IJS 在里面感受不到任何方向，无法被"推"出禁区；
`scipy.ndimage.distance_transform_edt` 得到的深度场处处指向最近的禁区边界，
提供明确的逃离方向。这与 §1.8 中"高程用双线性插值保连续、掩膜用最近邻"
的既有取舍是同一考虑。

#### 局限

1. **继承 OSM 建筑完备度的局限**（见 §2.6）：密度低的区域可能只是 OSM 无记录，
   郊区与村镇尤甚。故密度分区**只用于可行性约束，不进入成本模型**（不计拆迁费）。
2. **V5（体量指标）证据不足**：全集仅 4806/22590（21.3%）建筑带 `building:levels` 标签，
   其余按 1 层计，且标签最大值 103 层在本区域明显属异常标注。故体量指标仅作参照，
   未被选用。
3. **`M-A ∩ Tier2 = 0` 是设计保证而非验证结果**：它是标定规则的必然结果，
   不能用来论证某个版本"更好"。真正的区分量是 `M-A ∩ Tier1`、
   走廊带最窄可通宽度与禁区簇的形态。

## 3. 实测数据

| 文件 | 内容 |
|---|---|
| `measured/数据.xlsx` | 既有北环高速 GPS 实测中线，**14018 点**，字段 `Latitude / Longitude / Altitude / Distance / R` |
| `measured/北环高速现状桥梁隧道统计.xlsx` | 现状桥梁、隧道长度统计（用于桥隧计费基准与校准） |
| `measured/data_loader.py` | 加载与投影脚本 |

**坐标投影**（`data_loader.py::load_alignment`，对应论文式 3.3–3.4）：
以中线**首点**为原点的局部平面近似

```
lat0, lon0 = 首点纬经度(弧度)
X = R_E · cos(lat0) · (lon − lon0)      # 东向, m
Y = R_E · (lat − lat0)                  # 北向, m
R_E = 6378137.0                          # WGS84 长半轴
```

**全项目统一使用这一个投影**。DEM 栅格像元、OSM 折线顶点、建筑轮廓顶点
全部按这同一公式换算到该局部坐标系 —— 这是各图层能够正确叠合的前提。
绘图脚本中都写有包围盒自检，一旦投影原点不一致会直接报错而非画出错位的图。

## 7. 已知局限汇总（一处集中列出，便于论文如实声明）

1. **DEM 空间分辨率被过采样**：像元 8.78 m，底数约 30 m（SRTM），
   有效分辨率约 30 m 量级。适用于数百米尺度地形，不适用于微地形判读。
2. **准天然地面是插值近似**：建路前实测地形不可得；其作用是消除现状与优化方案之间的
   土方计费口径偏差，不是还原历史真实地面。
3. **DEM 绝对高程有系统偏差**：已用常数 `BIAS_M = 1.57 m` 消除中位偏差，
   但逐点残差仍存在（相关系数 0.915）。
4. **OSM 建筑图层完备度受数据源限制**：数量已与 OSM 数据库完全一致，
   但 OSM 本身在国内城区未必 100% 完备；"图上空白"≠ 实地无建筑。
   **正因此建筑数据不进入目标函数。**
5. **OSM 是众源数据、有时效性**：本项目使用的是特定时刻的快照
   （障碍物 2026-08-09、建筑 2026-08-11），数据会随社区编辑变化；
   所有派生文件均记录了快照时刻。
6. **立交名称与地理位置反序**：论文表中立交名称与实际东西位置呈反序对应
   （见 §2.5），不影响计算但影响读图。
7. **密度分区继承 OSM 建筑完备度局限**：密度低的区域可能只是 OSM 无记录（郊区、村镇尤甚）。
   因此密度分区**只作可行性约束、不进入成本模型**（不计拆迁费），且 Tier1 允许穿越。
8. **`M-A ∩ Tier2 = 0` 是设计保证而非验证结果**：它是"θ_forbid 取现状线位最大密度之上"
   这一标定规则的必然结果，不能用来论证分区方案的优劣。
9. **DEM 实际南界比标称 bbox 短约 555 m**：栅格取整 5 张 z14 瓦片（11238 m），
   而 bbox 纬度跨度需约 11800 m（6 张），实际南界为 lat 23.09998（见 §1.5）。
   线位 + ±2500 m 走廊带完全落在 DEM 内，**不影响采样与优化**；
   唯一后果是叠加图最南端一小片建筑没有地形底色。
